# Decision 与回复可靠性

## 2026-10-10 日志排查依据

165 服务器最近一次生产运行（北京时间 2026-10-09 20:52–21:58，含重启回放）的数据库事件中，有 151 次 Decision：119 次 ignore、31 次 reply、1 次 start_task；71 次重试、3 次最终失败。成功发送 55 个气泡，3 次 ReplyInterrupted，1 次 bot_chat 空正文。该实例使用 V5 数据库，尚未使用 ADR-0008 的人物简档/固定回复快照。

Docker 日志显示服务收到了停止请求，SIGTERM 后等待 10 秒仍未退出而被强杀（137）；`hasBeenManuallyStopped=true`、`OOMKilled=false`。不能根据 137 推断为内存不足，也不能从这些日志判断谁发起了停止。

小样本复现发现 `space-bunny-free` 上游有时返回 `finish_reason=tool_calls`、空 content 和未经声明的 bash 调用；旧代码只取 content，因此记录为 JSON 解析失败。这能解释一部分重试，不能据此认定全部 71 次都是同一原因。收到的工具调用没有被执行。

## 输入与输出约束

- `chat` 网关请求显式带 `tool_choice=none`。本接口没有声明原生工具，Agent 仍使用既有 JSON 工具循环；不把上游擅自返回的工具调用解释成任务或聊天文本。
- 返回原生工具调用、长度截断或拒绝时记录明确错误，不发送残缺正文。Decision 提供有效的最小 JSON 示例、明确空技能目录，只做分类，不查文件或执行指令。
- JSON 首次校验失败记录错误与响应字符数，再重试一次；不把完整模型输出、推理字段或凭证写进诊断日志。网络/协议错误保留原有直接降级行为，避免无条件重试。
- Decision 额外读取窗口前最多 6 条近期消息，每条正文约 160 字，仍来自同一快照并计入 8,000 字符 state 上限。熟悉度为零只表示不熟悉，不能推断反感或作为拒绝正常提问的唯一理由。
- `start_task`、`invoke_skill` 新增 `request_quote`：4–240 字，必须匹配 anchor 开头的原话，并通过保守的中文请求开头/否定检查；任务目标必须非空且不超过 800 字。未满足时，直接 @、私聊、引用 Bot 的消息退回 reply，普通分享退回 ignore。可直接基于资料解释或总结的问题优先 reply，不自动替长文分享创建任务。

请求开头检查支持“请帮…、帮我…、请运行…、云团，帮我…”等形式；转述、被引用资料和单纯“请问”不能作为执行请求。它是保守的防误触发检查，不能证明任意自然语言的授权语义；特殊说法可能退回聊天。工具自身的权限和沙箱限制仍独立生效。

## 正文生成与发送

- 未创建过任何人格版本时，启动过程初始化一个可在面板编辑的默认版本；有管理员历史版本时不覆盖、不重新激活。默认人格保持友好自然，同时禁止编造自己的经历、跨群活动和操作结果。
- Bot 上下文显式标记本轮没有工具、跨群历史查询或执行结果；行为规则禁止把“刚去看了”“已经运行过”等无证据叙述当作事实。仅有旧 Bot 回复也不能证明操作发生过。此为上下文和提示约束，不是模型事实正确性的硬保证。
- `reply_len` 已进入 Bot system 提示：short 优先一两句、约 80 字；medium 通常约 200 字；long 按需要展开。发送侧 short 最多 1 泡、medium 最多 2 泡、long 遵循配置泡顶，均不超过配置泡顶；超出的完整句合并，不截掉正文。提示字符数计入总预算，字数仍是生成建议。
- 空正文使用同一 system/user 重试一次，仍空则记录失败；未新增群内通用错误提示。工具调用/拒绝/网络错误不走空正文重试。
- 普通插话不再取消已入队气泡，原回复对象保持不变，落实 ADR-0007。明确取消/更正、高优先级独立窗口的完整调度仍未实现。

## 2026-10-10 切句与群聊打扰度

用户反馈“一句话被拦腰切成两条，或者符号残留”，并要求降低回复积极度。本轮采用保守切句和较安静的群聊策略：

- `‖` 是候选断点；前段没有完整句末、引号/括号尚未闭合、后段只有脱落标点时接回同一条，不能在逗号或半句处拆成两个消息。模型也被要求只在完整句子之间使用分隔符。
- 代码中的竖线、闭包和指令字样保持原样；普通正文里的纯分隔符/纯指令不再回退成原始控制符发送。容忍 `::at` 贴着正文或位于句尾。独立 `||`/`｜｜` 控制行可以识别，正文中的双竖线不作全局替换。
- `bubble_char_cap` 保留配置键，含义明确为拆句目标字数；仅在完整句末拆分，长单句、代码、链接、引用可以超过目标，不能靠拦腰切断满足字数。未实现独立的 QQ 平台长度兜底或复杂语义断句，异常长单句仍可能发送失败。
- 群聊的收尾/附和（如“嗯、哈哈、谢谢、收到”）即使带 @ 也默认不再接话；引用回答 Bot 具体问题时保留处理机会。普通感叹、他人之间的引用对话不主动加入。私聊不受此群聊规则影响。
- 没有直接 @、引用 Bot 或以“云团”开头叫它时，只有开放问题候选可被主动回复，且最近 120 秒已有 Bot 发言则压成 ignore。候选问题识别是保守的文字规则，最后仍由模型决定是否回答；不能保证理解任意省略表达。120 秒目前为代码固定策略，不是面板新增配置。
- 冷却读取当前实际发送记录，因此旧窗口排队/回放也考虑刚刚发送的消息；这个即时限流检查不替换原回复快照。它不是发送队列的全局预留配额，尚未发出的消息不计入发送记录。
- 主动回复强制 short、mention=false；正文回答完就停，不用无关反问或邀请继续聊来延长会话。原有 Prefilter 达到气泡顶即拦截，修复多放行一条的边界。

## 停机

启动回放前注册 Unix SIGTERM/SIGINT，回放期间也能响应。停止时拒绝新的 NapCat 连接和业务消息，保留已有连接的发送回执；停止管线、任务 runner、偷图及后台定时器。管线 worker 归属于 JoinSet，取消 dispatcher 时一起取消。

回复入口关闭后，已入队消息最多排空 5 秒；超时取消发送 worker，日志用 `drained=false` 明确标记。随后给 MCP 收尾最多 1 秒，停止 tracer，检查 SQLite checkpoint 的 busy 返回值并退出。不会声称超时情况下全部回复已送达；任务取消后沿用既有重启恢复规则，不重放已开始的工具操作。

## 验证入口

- `cargo test --workspace`：消息闭环、插话不打断、空正文同快照重试、任务证据拒绝、默认人格不覆盖等。
- `cargo test -p yuantuan-core shutdown_drains_jobs`：队列排空与超时取消正在等待的发送器。
- `cargo run --locked -p yuantuan-core --example verify_bot -- /path/to/providers.toml`：12 个合成 Decision 样本（含收尾/感叹/直接提问）和 2 个无执行依据的正文样本。只写临时库，不连接 QQ、不调用任务工具；会调用所配置模型并产生少量用量。模型文字需人工核对，样本不能替代生产幻觉率评估。

- `python3 deploy/verify-bot-runtime.py /path/to/yuantuan /path/to/source.db`：Linux 下用只读 SQLite 备份创建独立副本，在无网络、无凭证、无 QQ 接入的临时容器中验证 V6 迁移及正常运行/启动回放时的 SIGTERM，最后删除临时容器和副本。

缺少记录也不能推断从未发生：过去活动未知时说明无法确认，不编造否定经历。
