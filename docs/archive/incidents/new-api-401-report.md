# new-api 401 故障复盘

[文档索引](../../README.md) · [归档索引](../README.md)

> 历史记录：以下背景、测试与剩余事项对应原记录日期。归档仅改变资料归属，不扩展当时的验收范围。

> 状态：模型调用链路已修复。故障记录始于 2026-10-08，修复于 2026-10-09。本文时间均为北京时间（UTC+8）。

## 1. 结论与影响

服务器把脱敏占位符 `[redacted]` 当成真实 API key，写入了机器人配置中的 `api_key_env` 字段。后续多次手写 HTTP 测试也使用了这个占位符，因此返回 `401 Invalid token`。

Kimi 配置中保存的是真实密钥。直接读取该密钥发起普通 Python HTTP 请求即可成功，不需要 Kimi 专用请求头。原报告中“同一把 key”和“所有非 Kimi 请求都失败”的前提不成立。

受影响的是 `yuantuan` 的 LLM 调用：`decision`、`bot_chat` 和 `agent_exec` 三个角色都绑定了错误配置的 `spacebunny` provider。修复后已验证容器内模型调用成功；完整群聊收发流程尚未实测。

上述结果来自对实际配置、项目对应的历史测试记录和实时请求的核对。真实密钥只在内存中读取、比对和传递，未写入本文。

## 4. 修复过程

1. 备份服务器上的 `yuantuan-providers.toml`。备份位于同一目录，文件名为 `yuantuan-providers.toml.before-401-fix-20261009-003215`。
2. 将 `[provider.spacebunny]` 下的 `api_key_env` 替换为 Kimi 配置中已验证可用、对应同一服务地址的真实密钥。密钥通过 SSH 标准输入传递。
3. 保留原有服务地址、三个角色的绑定和 `space-bunny-free` 模型，重启 `yuantuan` 容器加载配置。
4. 从重启后的容器读取实际配置，发起最小模型请求并检查容器状态和日志。

## 6. 对原报告的更正

| 原判断 | 更正 |
| --- | --- |
| Kimi 与所有失败请求使用同一把 key | 实际配置和失败测试中存在字面值 `[redacted]`，该前提不成立 |
| 所有非 Kimi 客户端请求都失败 | 历史记录和本次实测均有普通 HTTP 客户端调用成功的结果 |
| 剩余原因只能是特殊请求头或客户端指纹 | 使用真实密钥的普通请求即可成功，这些假设不能解释本次故障 |
| `X-New-Api-Version: v0.0.0` 能证明服务被修改 | [公开源码](https://github.com/QuantumNous/new-api/blob/main/common/constants.go)的默认版本号即为 `v0.0.0`；仅凭该响应头无法判断服务是否修改过鉴权逻辑 |
| 请求 ID 中相同的片段能证明成功和失败请求落到同一后端 | 原报告没有提供足够的成功请求对照，不能据此得出该结论 |

原求助稿中的排除矩阵建立在凭证相同的假设上，不能继续作为排除依据。抓包代理脚本、特殊请求头猜测和求助清单已从正文移除；本次故障的有效结论以本复盘为准。

## 7. 后续排查要点

- 从真实配置源读取密钥，不要复制报告、聊天或日志里的脱敏占位符。比较凭证时仅输出是否一致等诊断信息。
- 先核对运行时实际使用的地址、provider、密钥和模型，再比较客户端、代理或网络路径。
- 对照测试保持请求参数一致；修改配置后确认进程已重新加载，并从实际运行环境验证。
- 记录已验证范围和未验证事项，避免把“接口调用成功”扩展为“完整业务流程已恢复”。
